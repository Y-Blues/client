# client navigateur : plan d'implémentation (v2 — refonte « vrai framework »)

**Goal :** remplacer l'`ApiClient` HTTP bespoke de la v1 par quatre composants natifs (`RemoteCrud`, `RemoteDrafts`, `RemoteItemCatalog`, `RemoteServiceEndpoint`) implémentant réellement `ICrud`/`IDrafts`/`IItemCatalog`/`IServiceEndpoint`, auto-découverts par le vrai `ycappuccino.core.framework.Framework` dès que `bundle_prefix` contient `"ycappuccino.client"` — le code applicatif ne dépend que des interfaces `api`, jamais de `ycappuccino.client` directement. Documenter précisément, sans les diluer, les risques navigateur explicitement acceptés par l'utilisateur (thread OS réel pour `AsyncRunner`, PyYAML, `Framework.init` et son chemin de fichier, COOP/COEP).

**Architecture :** voir `client/docs/superpowers/specs/2026-09-15-client-design.md`. Le §0 (import-clean) reste le socle ; le §0bis (risques navigateur) et le §2 (décisions A.1–A.5) gouvernent tout le reste.

**Tech Stack :** inchangé (Python ≥ 3.10, `uv_build`, `unittest`), sauf que `ycappuccino-core` est maintenant une vraie dépendance d'exécution (le test d'intégration démarre un vrai `Framework`), pas seulement transitive.

## Contraintes globales

- Ne jamais modifier `api`, `core`, `storage`, `endpoints_storage`, `endpoints_service`, `http_server`, `permissions_app`, `scripts`, `scheduler`, `swagger`, `remote`, `component-creator`. Seul `hosts` reçoit un changement additif isolé (Partie C, commit séparé).
- Commit après chaque étape validée, dans `client` : `git -c user.name="Aurélien Pisu" -c user.email="aurelien.pisu@gmail.com" commit -m "client: <message court>"`. Un seul commit dans `hosts`, séparé : `hosts: <message court>`. Jamais de `git push`, jamais de réécriture d'historique.
- Toute affirmation sur le comportement en navigateur réel doit être marquée explicitement "non vérifié" — jamais prétendre l'avoir testé.
- Commande de test, depuis `client/` : `uv run python -m unittest discover -s src/unittest/python`. Depuis `hosts/` : la même.

## v3 : `make_remote`, fabrique générique par réflexion (demandé le même jour, après la v2)

Voir spec §9 pour les cinq conventions complètes et leurs limites. Résumé des étapes :

- [x] **Spec d'abord** : §9 écrit et commité (`fc17918`) avant tout code, avec les cinq conventions verbatim et leurs limites honnêtes (§9.4), conformément à la discipline du reste de cette migration.
- [x] **`remote_proxy.py`** : `make_remote(interface, resource, **extra_deps)` — `_build_init` (constructeur forgé par `exec`, signature réelle et introspectable), `_build_method` (une méthode générique par méthode abstraite de l'interface, même signature d'appel), `_RemoteProxyBase` (`start`/`stop`/`_dispatch`/résolution de cache/résolution `item_id → plural`).
- [x] **`components.py`** : les quatre affectations d'une ligne, remplaçant `remote_crud.py`/`remote_drafts.py`/`remote_item_catalog.py`/`remote_service_endpoint.py` (supprimés).
- [x] **Bogue réel trouvé et corrigé pendant l'implémentation** : le déclencheur de la convention 3 (dérogation littérale) incluait à tort `params`/`body` seuls, alors qu'`ICrud`/`IDrafts` utilisent aussi ces noms génériquement — corrigé pour ne déclencher que sur `method`/`extra_path` (les deux seuls noms jamais utilisés autrement). Sans ce correctif, `ICrud.get_one`/`get_many` (qui ont un paramètre `params`) partaient par erreur dans la branche `IServiceEndpoint`.
- [x] **Tests unitaires réécrits** : un test par méthode des quatre interfaces contre `ycappuccino.client.components`, vérifiant le verbe/chemin/corps/query exacts — en particulier le trio `save`/`discard`/`publish` d'`IDrafts` (le cas le plus piégeux : `discard` ne doit **pas** avoir de suffixe `/discard`, vérifié explicitement).
- [x] **Deuxième bogue réel trouvé, plus profond, pendant l'écriture du test d'intégration** : publier un faux `IHttpFetcher` (`Optional[IHttpFetcher]`) depuis un paquet de test échouait de façon déterministe — pas une fois sur deux, **toujours** — parce que `HttpTransport` vit dans l'espace de noms `ycappuccino.*` : exactement le défaut déjà documenté dans `hosts/servlet.py`. Diagnostiqué par instrumentation directe (`HttpTransport.__init__` loggé : `fetcher=None` à chaque fois, alors que le service était bien présent dans le registre Pelix au même instant) et isolé par des reproductions minimales. Corrigé en abandonnant le mécanisme `IHttpFetcher`/DI pour le test d'intégration, au profit d'un remplacement direct de `ycappuccino.client.pyodide_transport.pyodide_transport` (affectation Python simple, hors de portée du registre de services Pelix) — voir `test_client_framework.py` et spec §9.2 pour le détail complet. `IHttpFetcher` reste dans le code, documenté comme fragile au travers de cette frontière précise.
- [x] `test_client_framework.py` gardé sans changement de fond : même `bundle_prefix` (`PACKAGE`, `ycappuccino.client`), même composant `Demo` ne dépendant que d'`ICrud`/`IItemCatalog`/`IServiceEndpoint`, mêmes assertions — seul le mécanisme de transport falsifié a changé.
- [x] README + spec mis à jour, `hosts` non touché (déjà commité séparément).
- [x] `uv run python -m unittest discover -s src/unittest/python` -> `OK`, 55 tests, vérifié stable sur plus de 10 exécutions consécutives (contre une exécution parfois lente/en échec avant le correctif du deuxième bogue, qui n'était pas un problème de charge machine comme d'abord supposé, mais le bogue lui-même).
